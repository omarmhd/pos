# تصميم فصل المهام (Maker-Checker) للعمليات المالية

**المرجع التدقيقي:** H-5
**الحالة:** الأساس مُهيّأ (صلاحية الاعتماد) — يلزم بناء آلة الحالة (Runtime) كجهد مخصّص.
**التاريخ:** 2026-06-14

## 1. المشكلة

حاليًا تُنشأ القيود اليدوية والعكس والإقفال وتُرحَّل **بالعملية نفسها وبصلاحية واحدة**، دون موافقة ثانية. التدقيق الخارجي يتطلب **فصل من يُنشئ عمّن يعتمد** (4-eyes).

## 2. الأساس المُنفَّذ الآن

- صلاحية جديدة: **`journal_entries.approve`** (معتمِد) منفصلة عن `journal_entries.create` (مُنشئ).
- ملاحظة: بعض الوحدات تملك فصلًا جزئيًا أصلًا (`sales.post`, `purchases.post`, `accounting.post/reverse/year_end_close`).

## 3. آلة الحالة المقترحة (Runtime — يُبنى لاحقًا بحذر + اختبارات)

أضف حقل `approval_status` إلى `journal_entries`: `draft → pending → approved` (+`rejected`).

```
[مُنشئ] ينشئ قيدًا           → approval_status = pending, posted_at = null (لا يدخل الأرصدة)
[معتمِد ≠ المُنشئ] يعتمد     → approval_status = approved, posted_at = now() (يدخل الأرصدة)
[معتمِد] يرفض               → approval_status = rejected (يبقى للأثر، لا يُرحَّل)
```

### نقاط الربط في الكود
- `LedgerPostingService::buildEntry()`: يُنشئ القيد بحالة **pending** بدل الترحيل الفوري (لا `posted_at`).
- التقارير (ميزان المراجعة/القوائم/الأرصدة): تحسب فقط القيود `approved` (`whereNotNull('posted_at')` أو `approval_status='approved'`).
- نقطة اعتماد واحدة: `JournalEntryController@approve` تتحقق:
  - `auth()->user()->can('journal_entries.approve')`
  - `entry.created_by !== auth()->id()` (منع اعتماد الذات).
  - `PeriodLockService::assertOpen(entry_date)`.
  - إعادة فحص التوازن قبل الاعتماد.

### القيود الآلية (مبيعات/مشتريات POS)
خياران:
1. **اعتماد تلقائي** للقيود الآلية الموثوقة (POS/فواتير مُولّدة آليًا) لتفادي تعطيل العمليات اليومية، مع إبقاء **اليدوية والعكس والإقفال** خاضعة للاعتماد اليدوي. (موصى به للتجزئة.)
2. اعتماد الكل (يبطئ POS — غير عملي).

## 4. الأثر والمخاطر

- **عالي الحساسية:** يلمس محرّك الترحيل والتقارير. **يجب** أن يصاحبه اختبارات شاملة (قيد pending لا يظهر في ميزان المراجعة؛ بعد الاعتماد يظهر؛ منع اعتماد الذات؛ منع الاعتماد على فترة مقفلة).
- يُنفَّذ خلف **Feature Flag** (`Setting::get('maker_checker_enabled')`) للتفعيل التدريجي.

## 5. خطة التنفيذ المقترحة (3–5 أيام)

1. Migration: `approval_status` + `created_by` (إن لم يوجد) + فهرس.
2. تعديل `buildEntry` (خلف العلم) + اعتماد تلقائي للمصادر الآلية.
3. `approve/reject` + التحقق من فصل المُنشئ/المعتمِد.
4. تصفية التقارير على المعتمَد.
5. شاشة "قيود بانتظار الاعتماد" + إشعار.
6. اختبارات + توثيق الدليل.
